# Entra ID 同期属性・IDトークンクレームの確認依頼

## 1. 依頼概要

社内Webアプリ「資料みて！」では、サインインした利用者の所属コードをMicrosoft Entra IDのIDトークンから取得する予定です。

現在、オンプレミスActive Directory（以下、オンプレAD）からMicrosoft Entra IDへグループを同期しており、Entra ID上の所属グループ名はオンプレADと同一であると認識しています。

本書では、Entra ID管理者に、同期されている属性とIDトークンへの発行可否について確認をお願いします。設定作業の依頼は本書に含みません。

## 2. 対象情報

| 項目 | 内容 |
|---|---|
| 対象アプリ名 | 資料みて！ |
| 環境 | production / staging |
| テナントID | 管理者確認用。リポジトリには記載しない |
| アプリケーション（クライアント）ID | 管理者確認用。リポジトリには記載しない |
| 認証方式 | OpenID Connect Authorization Code Flow |
| 対象トークン | IDトークン |
| 既存App Role | `User`、`Admin` |
| 所属コード例 | `ZAA535-A`、`ZAA090-A` |

## 3. 想定する利用方法

アプリ開発者側では、サインイン利用者の所属コードをIDトークンの文字列配列として受け取る方式を検討しています。

想定するIDトークンの例:

```json
{
  "oid": "ユーザーのObject ID",
  "roles": ["User"],
  "groups": [
    "ZAA535-A",
    "ZAA090-A"
  ]
}
```

- 所属が複数ある場合はすべて受け取る
- 所属がない場合はアプリ側でアクセスを拒否する
- 既存の`User`、`Admin` App Roleは、従来どおり`roles`で受け取る
- グループを`roles`として発行しない
- 所属コード取得を目的としたMicrosoft Graph権限は追加しない

## 4. 期待する効果

所属コードをOIDCのIDトークンクレームとして取得できれば、各アプリが所属情報を取得するためだけにMicrosoft Graphを呼び出す必要がなくなります。この方式は「資料みて！」だけでなく、所属コードを利用するすべてのOIDC対応アプリに共通して適用できるため、全社的な開発効率を大きく向上させる効果があります。

主な効果は次のとおりです。

- アプリごとのMicrosoft Graph呼び出し実装が不要になる
- `GroupMember.Read.All`などのGraph権限申請と管理者同意を削減できる
- Graphアクセストークンの取得、保持、更新に関する実装が不要になる
- Graph APIのページング、タイムアウト、再試行、障害時処理を各アプリで実装する必要がなくなる
- 所属コードの取得方式をOIDCクレームに統一でき、アプリ間の実装差異を減らせる
- 新規アプリは共通のクレーム検証処理を再利用でき、開発・テスト・セキュリティレビューを効率化できる
- 所属情報の発行元をEntra IDへ集約でき、認証時点の情報として一貫して利用できる

このため、所属コードのクレーム発行は単一アプリ向けの個別対応ではなく、今後の社内アプリ開発で再利用できる共通認証基盤の改善として検討する価値があります。Entra ID側で発行する属性、値の形式、変更管理を標準化できれば、アプリ開発者は業務機能の実装に集中できます。

## 5. Entra ID管理者への確認事項

### 5.1 オンプレADから同期されているグループ属性

対象の所属グループについて、次を確認してください。

| 確認事項 | 管理者回答 |
|---|---|
| オンプレADから同期されたグループか | |
| Entra ID上のグループ種別 | |
| `displayName`の値の形式 | |
| `sAMAccountName`の値の形式 | |
| `onPremisesSamAccountName`が同期されているか | |
| `ZAA535-A`形式の所属コードが格納されている属性 | |
| 対象属性がすべての所属グループで一意か | |
| 対象属性がグループ名変更時にも維持されるか | |

実際のグループ名や利用者情報は本書へ記載せず、属性名とマスキングした値の例だけを回答してください。

### 5.2 IDトークンへ発行可能な属性

オンプレAD同期グループのクレームとして、希望する`ZAA535-A`形式の値をOpenID ConnectのIDトークンへ発行できるか確認してください。

| 確認事項 | 管理者回答 |
|---|---|
| `sAMAccountName`をIDトークンのグループクレームへ発行可能か | |
| `NetBIOSDomain\sAMAccountName`形式で発行されるか | |
| `DNSDomainName\sAMAccountName`形式で発行されるか | |
| `displayName`だけに所属コードがある場合も発行可能か | |
| 発行値は文字列配列になるか | |
| 複数所属をすべて発行可能か | |
| 対象テナント固有の制限があるか | |

第一候補は、所属コードと一致する`sAMAccountName`を標準の`groups`クレームへ発行する方式です。

### 5.3 所属グループの構成

アプリでは利用者本人の直接所属を利用する設計を検討しています。現在の所属グループ構成について、次を確認してください。

| 確認事項 | 管理者回答 |
|---|---|
| 対象利用者は所属グループの直接メンバーか | |
| 入れ子グループ経由の所属が存在するか | |
| 動的グループを使用しているか | |
| 所属変更がEntra IDへ反映されるまでの通常の所要時間 | |

### 5.4 標準グループクレームで実現できない場合

希望する所属コードが`displayName`にだけ存在し、標準のグループクレームで発行できない場合は、対象テナントで利用可能な方法を確認してください。

| 確認事項 | 管理者回答 |
|---|---|
| カスタム名のグループクレームへ変換できるか | |
| Claims Mapping Policyを利用できるか | |
| 正規表現による抽出・変換を利用できるか | |
| カスタムクレームに必要なEntra IDライセンス | |
| 対象アプリだけにポリシーを適用できるか | |
| トークン署名や既存クレームへの影響があるか | |

上記の方法を利用できない場合は、その旨と、Entra ID管理者として推奨する代替案を回答してください。

## 6. 希望する回答

以下の形式で回答をお願いします。

```text
1. 所属コードが格納されている同期元属性:
2. Entra ID上の対応属性:
3. IDトークンへの発行可否:
4. 発行可能なクレーム名:
5. 発行される値の形式:
6. 直接所属・入れ子所属の状況:
7. 所属変更の反映時間:
8. テナントまたはライセンス上の制限:
9. 標準グループクレームで実現できない場合の推奨方式:
10. その他の注意事項:
```

回答時にIDトークン全文、実際の利用者情報、グループObject IDなどをメール、チャット、チケットへ貼り付けないでください。必要な場合は、値をマスキングした属性名と発行形式だけを共有してください。
